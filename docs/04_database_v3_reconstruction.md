# 能力图谱数据库 v3 重构说明

## 1. 本轮交付

本轮采用“复制后扩展”的非破坏性方案：

- 数据源：`embodied_ai_jobs_v2.db`
- 新数据库：`embodied_ai_jobs_v3.db`
- 旧数据库 `embodied_ai_jobs.db`、`embodied_ai_jobs_v2.db` 均未修改
- v2 的 23 张业务表在 v3 中逐表保留，行数与逐值摘要完全一致
- 在保留原数据的基础上，新增能力本体、能力别名、技能映射、岗位能力画像、岗位相似度和图谱视图

v3 当前是图谱后端下一阶段的数据库基础。现有前后端仍连接 v2，待 v3 API 完成并通过接口测试后再切换，避免本轮数据库改造影响已运行的 MVP。

## 2. 能力本体结构

能力本体采用四层结构：

```text
具身智能（L0）
└─ 一级能力方向（L1，6 个）
   └─ 二级能力类别（L2，25 个）
      └─ 三级能力/技术变体（L3，169 个）
```

六个一级能力方向及二级分类如下：

| 一级能力方向 | 二级能力分类 |
|---|---|
| 战略与经营管理能力 | 战略决策与领导、业务与项目管理、创新与问题解决 |
| 研究、设计与算法能力 | 基础与前沿研究、机器学习与模型开发、视觉感知与多模态、定位建图与状态估计、运动规划与控制、架构与产品设计 |
| 工程开发与实现能力 | 软件开发、机器人中间件与系统集成、AI框架与计算平台、仿真与工程工具、嵌入式与电子开发、机械/执行器与感知硬件、数据工程与云原生 |
| 测试、生产与供应链能力 | 测试与验证、生产制造、供应链与质量 |
| 商业化、服务与支持能力 | 市场与品牌、销售与业务拓展、部署运维与客户成功 |
| 职能支撑能力 | 人力资源与组织协作、财务/法务与合规、综合与专业支持 |

### 2.1 旧技能处理原则

原库 136 个技能全部建立了唯一的主映射，没有丢弃或直接改写原记录：

- 119 个规范化三级能力由旧技能归并得到
- 135 个映射为 `exact`
- ROS2 作为 ROS 的技术代际变体，1 个映射为 `variant`
- `NumPy/numpy`、`VO/vo/vO/Vo/视觉里程计`、`PROFINET` 大小写、`RGBD/RGB-D`、`VIO/vio`、`TPU/tpu` 等重复写法被归入统一能力，并保留原写法作为别名
- 规范化键保留 `+` 与 `#`，防止 C++、C# 被错误合并

### 2.2 新增和修缮的能力

针对原始技能库对非研发岗位覆盖不足的问题，新增 47 个待审核的三级能力，主要包括：

- 战略经营：战略规划、经营决策、技术路线决策、业务分析、研发项目管理、生态合作管理、创新管理
- 研究设计：机器人伦理与安全研究、实验设计与科研方法、系统架构设计、产品规划、用户研究、人机交互设计
- 测试生产：自动化测试、可靠性验证、功能安全验证、形式化验证、生产工艺设计、机器人装配与调试、精益制造
- 供应链质量：供应商管理、质量管理、采购与物料管理
- 商业化服务：市场研究、品牌营销、技术内容策划、解决方案销售、渠道管理、商务谈判、现场部署、机器人运维、远程诊断、客户成功、产品培训
- 职能支撑：招聘与人才配置、绩效管理、薪酬管理、培训与组织发展、财务分析、预算管理、法律合规、知识产权管理、风险控制、IT支持、数据安全与隐私、标准化管理、行政与设施管理

同时建立 4 条明确的技术变体关系：

- C++17开发 → C++开发
- C++20开发 → C++开发
- C++23开发 → C++开发
- ROS2开发 → ROS开发

这些专家补充节点没有伪装成已从岗位证据中抽取的事实：其 `source_type` 为 `expert_seed`、`review_status` 为 `pending`，便于后续人工确认、修改或删除。

## 3. 新增的数据结构

| 表/视图 | 用途 |
|---|---|
| `ontology_versions` | 能力本体版本及当前版本标识 |
| `capability_nodes` | L0-L3 能力层级节点、来源、置信度、审核状态 |
| `capability_aliases` | 技能别名、缩写、拼写变体 |
| `capability_relations` | `VARIANT_OF` 等非树形能力关系 |
| `skill_capability_mappings` | 旧技能到新能力节点的可追溯映射 |
| `career_aliases_v3` | 增强的职业别名表，保留别名类型和审核信息 |
| `job_capability_profiles` | 岗位—能力画像、权重、证据数、置信度 |
| `job_similarity_runs` | 岗位相似度算法运行批次和参数 |
| `job_similarities` | 岗位间相似度及分项得分 |
| `job_similarity_explanations` | 每条相似关系的共享能力解释 |
| `career_communities` | 后续职业领域聚类结果的存储位置 |
| `graph_layout_cache` | G6 布局坐标缓存 |
| `v_capability_tree` | 能力树查询视图 |
| `v_capability_summary` | 能力节点覆盖统计视图 |
| `v_job_capability_detail` | 岗位能力画像明细视图 |
| `v_job_similarity_detail` | 岗位相似关系明细视图 |
| `v_graph_v3_nodes` / `v_graph_v3_edges` | 图谱 API 可直接转换的统一节点/边视图 |

层级触发器会拒绝以下非法写入：多个根节点、父子层级不连续、跨本体版本挂接、变体节点出现在非三级层级等。

## 5. 审核状态与已知边界

- 根节点和六个一级能力方向已标记为 `approved`
- 25 个二级分类、169 个三级节点、全部旧技能映射和全部相似关系均标记为 `pending`
- 当前岗位能力权重采用基于覆盖频率的 IDF 基线，因为旧表中的关系权重统一为 0.8，不能直接解释为“必备/重要/加分”
- 相似度是 `career-sim-v1-idf-topk` 研究基线，保留余弦、Jaccard、层级得分、双向覆盖率和共享能力解释
- 原始岗位技能存在过度共现和噪声，因此这 85 条相似关系不能直接作为最终职业领域划分；应在证据重抽取、能力重要性识别和人工抽样审核后重新计算

## 6. 迁移和校验命令

在项目根目录执行：

```powershell
python .\scripts\migrate_database_v3.py `
  --source .\embodied_ai_jobs_v2.db `
  --target .\embodied_ai_jobs_v3.db `
  --migration .\database\migrations\002_capability_career_graph_v3.sql `
  --report .\database\v3_migration_report.json

python .\scripts\verify_database_v3.py `
  --source .\embodied_ai_jobs_v2.db `
  --target .\embodied_ai_jobs_v3.db `
  --report .\database\v3_verification_report.json
```

迁移脚本在目标文件已存在时会拒绝覆盖，避免误伤已审核的数据。若要重建，应先明确备份并只删除目标 v3 文件。

## 7. 下一步建议

1. 先做能力本体人工审阅接口：按 `review_status` 分页，支持重命名、移动层级、合并、别名调整、批准/驳回。
2. 重做 79 个未覆盖岗位的 JD 能力抽取，并为关系识别 `required/preferred/responsibility` 与证据句。
3. 基于审核后的岗位能力画像重算职业相似度，再进行社区发现和六大职业方向约束校正。
4. 实现 v3 图谱 API 后，将前端能力图谱和职业图谱分别接入 G6；通过回归测试后再把默认数据库从 v2 切换到 v3。
